# 工艺流程管理规范（Process Engineering）

> 版本: 1.0.0 | 状态: active | 适用范围: 全部开发阶段
> 定义：**阶段 + 关口** 的工艺流程、产出物依赖链、评审关口、能力组织判定、需求变更联动。

---

## 1. 工艺流程总览（阶段 + 关口）

```
Gate 0      Gate 1       Gate 2      Gate 3     Gate 4
需求通过    设计通过      计划通过     实现通过    交付通过
  │           │            │           │          │
  ▼           ▼            ▼           ▼          ▼
[P0 需求] → [P1 设计] → [P2 计划] → [P3 脚手架] → [P4 增量实现]
                                        │              │
                                        ▼              ▼
                                   （空壳可构建）   [P5 测试加固] → [P6 交付复盘]
```

### 关口（Gate）定义

| 关口 | 通过条件 | 产出物 |
------|---------|--------|
| Gate 0 需求通过 | 用户确认需求/假设（或 Auto 模式假设已记录） | request.md + prd.md |
| Gate 1 设计通过 | 显著决策有 ADR；模块契约明确 | architecture.md + ADR |
| Gate 2 计划通过 | 每任务有可验证 DoD | tasks.md |
| Gate 3 实现通过 | 每批测试绿 + 文档同步 | progress 日志 + 提交 |
| Gate 4 交付通过 | quality-gate 全绿 + 已知限制清单 | 测试报告 + runbook + 复盘 |

关口规则：

1. **关口不可跳过**（--minimal 模式也只压缩范围，不跳过产出物）。
2. 关口结论写入 `docs/04-progress/`（含"通过/返工"与理由）。
3. 返工闭环：Gate 失败 → 问题记录 → 修复 → 重新验证 → 关口通过。

## 2. 产出物依赖链

| 阶段 | 依赖输入 | 产出 | 被谁消费 |
------|---------|------|---------|
| P0 需求 | 用户原话 | request.md, prd.md | P1 设计、验收 |
| P1 设计 | prd.md | architecture.md, ADR | P2 计划、P4 实现 |
| P2 计划 | architecture.md | tasks.md | P3/P4 执行 |
| P3 脚手架 | tasks.md M0 | 骨架 + CI + .env.example | P4 实现基座 |
| P4 实现 | 架构 + tasks | 代码 + 单测 + progress | P5 加固 |
| P5 加固 | 代码 + 测试 | 测试报告 + 安全/性能清单 | Gate 4 |
| P6 交付 | 全部 | README + runbook + 复盘 + 经验 | 用户/运维 |

规则：上游未完成，下游只能做"依赖明确的部分"；发现上游问题，先记问题再顺流修正。

## 3. 需求变更联动流程

需求变更（用户一句话、评审意见、实现中发现矛盾）必须走：

1. **记录变更**：更新 `docs/00-request/request.md`（变更原因 + 新旧对比）。
2. **评估波及**：按 documentation.md §4.2 依赖矩阵评估：PRD 验收标准 / 架构 / 计划 / 测试 / 运行手册。
3. **决策记录**：变更显著时补 ADR（如范围扩大引入新组件）。
4. **顺流更新**：变更只能顺流传播，禁止只改代码不更新文档。
5. **验证**：受影响的验收标准重新跑测试，证据落 `docs/05-testing/`。

## 4. 能力组织判定（Agent vs 工具 vs 服务）

新增能力时先判定形态，避免"什么都用 Agent / 什么都写成工具"：

```
能力需要 LLM 推理或多轮决策？
  ├── 是 → Agent（独立角色：system prompt + 工具集 + 记忆 + 心跳）
  ├── 否 → 是确定性查询、被多方复用？
  │         ├── 是 → 工具/接口（函数、CLI、REST、MCP server）
  │         └── 否 → 普通业务函数/服务
  └── 需要长期积累上下文？→ 加记忆/会话管理
```

判定原则：

1. **能确定性实现就不用 LLM**（成本、延迟、可测试性）。
2. **能被多方复用就拆成工具/接口**（避免复制逻辑）。
3. **需要完整人格/上下文积累才建 Agent**（独立角色）。

## 5. 模块/组件拆分四维检验

拆分模块、Agent、服务前，用四维检验防止过度拆分：

| 维度 | 检验问题 | 冲突信号（不应拆/拆了要说明） |
------|---------|------------------------------|
| **上下文纯净度** | 拆分后各自的上下文是否加载互斥知识？ | 强耦合领域逻辑被拆散 |
| **时间尺度** | 两者的运行/会话模式是否一致？ | 高频短任务与长会话任务合并 |
| **风险边界** | 权限/影响范围是否兼容？ | 只读建议与写操作混在一个角色 |
| **生命周期** | 演进速度/发布节奏是否一致？ | 频繁变更与冻结稳定模块同仓 |

任何拆分/合并都必须有 ADR 或架构文档论证，禁止"凭感觉拆"。

## 6. 评审关口清单（Gate Review）

每个里程碑结束做一次评审（人 + Agent 均可），对照：

- [ ] 验收标准（PRD）全部有测试证据
- [ ] 契约（接口）变更已评估消费方（见 interfaces.md）
- [ ] 文档与实现一致（宣称 → 代码 → 证据 三对照）
- [ ] 安全/可靠性/性能清单过项
- [ ] 进度日志含失败记录（不是只报喜）
- [ ] 经验已沉淀、一般性教训已提升（铁律/规范）
- [ ] FILE_INDEX / MEMORY 同步
