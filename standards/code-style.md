# 代码风格与评审规范

## 1. 风格

| 规则 | 说明 |
|------|------|
| 用语言官方风格 | gofmt/gofmt、rustfmt、black、Google Java Format 等，构建/CI 强制 |
| 命名自解释 | 变量/函数/类名表达意图；禁止拼音缩写 |
| 小函数 | 函数一屏内可读；复杂逻辑拆解 |
| 显式优于隐式 | 类型/错误处理显式；避免魔法数 |
| 无死代码 | 未使用的 import/函数/配置在提交前删除 |
| 注释写"为什么" | 不写"是什么"（代码已表达）；复杂处注释意图 |
| 中文注释默认 | 跟随项目语言习惯；公共 API 建议双语 |

## 2. 提交规范

```
<type>(<scope>): <一句话摘要>
```

type: feat / fix / refactor / perf / test / docs / security / chore / revert

示例：`feat(auth): JWT 登录接口 + 吊销支持`、`fix(worker): 重试耗尽后进死信队列`。

## 3. 评审清单（Agent 自审 + 他人评审）

- [ ] 契约（接口签名）是否破坏消费方
- [ ] 错误处理是否完整（超时/异常/空值）
- [ ] 是否有硬编码凭证/环境值
- [ ] 并发安全（共享状态/竞态/CAS）
- [ ] 性能反模式（N+1/深分页/无界队列）
- [ ] 测试是否覆盖正反路径
- [ ] 文档是否同步（FILE_INDEX/进度）
- [ ] 是否有不必要的复杂度（YAGNI）

## 4. 复杂度治理

- 每个抽象/框架/中间件引入都要能回答："少了它会怎样？"答不上来就删。
- 代码里出现"临时/以后再说"的注释 = 欠债，当场记入 MEMORY.md 待办。
